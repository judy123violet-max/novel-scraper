# 工程化实践

单次抓取跑通后，用这四类实践让流程更稳、可复用、可恢复。借鉴自成熟爬虫工程（如 NovelSpider 的增量更新 + 任务队列思想），但适配 AI 代理的轻量工作方式。

## 1. 增量更新

同一本书可能被多次抓取（续更、补章、换源重抓）。每次都全量抓取浪费大量请求。

### 做法

抓取前先检查本地：

1. 若工作区已有该书的 txt 或中间 JSON，读取其章节列表。
2. 与目标站点的目录对比，只抓「缺失的章节」或「占位标记的章节」。
3. 补单章时，用章节标题精确定位，替换原占位标记（如 `（本章在源站无正文内容）`）。

### 补单章示例

```js
const txt = fs.readFileSync('book.txt', 'utf8');
const marker = '第307章 chapter101 夜雪';      // 当前章标题
const nextMarker = '第308章 chapter102 春归';   // 下一章标题
const i1 = txt.indexOf(marker);
const i2 = txt.indexOf(nextMarker, i1);
const newTxt = txt.slice(0, i1 + marker.length) + '\n\n' + content + '\n\n' + txt.slice(i2);
```

## 2. 断点续传

批量抓取几十上百章时，中途失败不应从头再来。

### 做法

- 抓取过程中，把「已抓章节」写入进度文件（如 `progress.json`，存 `{ 已抓章节id: true }` 或已抓章节名列表）。
- 失败章节跳过并记录，最后一并重试失败项。
- 关键：正文抓取和最终生成 txt 分离，进度只依赖中间态。

## 3. 中间态保存（两段式）

不要边抓边写 txt，而是分两段：

1. **抓取段**：把所有章节抓成 `raw.json`（含每章 `{ chapterid, title, txt }`），这一步可能失败、可重试。
2. **生成段**：从 `raw.json` 清洗 + 拼装，一次性生成最终 txt。这一步是纯本地处理，幂等、可反复跑。

### 好处

- 抓取与生成解耦，清洗规则调整后只需重跑生成段，不必重新抓取。
- `raw.json` 是原始证据，后续可导出 txt / epub / 其他格式。

## 4. 目录与正文分离

抓取分两个独立步骤：先拿完整目录（书名、作者、章节列表），再逐个抓正文。

- 目录通常一个请求就能拿全（SSR 目录页或 `booklist` API）。
- 正文是 N 个请求，是耗时和失败的主体。
- 分离后可以：先确认目录完整、章节数正确，再开始正文抓取；正文抓取可并发或分批。

### 任务拆分建议

```
第 1 步：探测站点（probe_site.mjs）       → 确定 SSR/CSR/登录/代理
第 2 步：拿目录 + 书籍信息                 → 1 个请求，拿到书名/作者/章节列表
第 3 步：抓正文（逐章，可并发）            → N 个请求，写 raw.json + progress
第 4 步：清洗 + 生成 txt                   → 纯本地，幂等
```

## 5. 并发与限速

- 并发抓正文可大幅提速，但要注意限速，避免触发站点反爬封 IP。
- 一般 3–5 并发、每请求间隔 200–500ms 是较安全的默认值。
- 若站点有 Cloudflare 或明显反爬，降为串行 + 更长间隔。
