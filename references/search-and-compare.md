# 全网搜索与资源比对

当用户**只给书名**、没有网址时，执行本流程。目标是找到资源最全、内容最完整的免费源，必要时正版 + 盗版拼接。

**引导用户补充信息**：书名必须，作者名强烈建议（作者名能大幅提高搜索命中率、排除同名干扰书）。用户只给书名时，可主动问一句「有作者名吗？」，没有也能继续搜，但有作者名会明显加速。

## 1. 全网搜索

用 `web_search` 工具，多关键词组合搜索。不要只搜一次，换关键词多搜几轮：

**基础关键词**（书名 + 常见后缀）：

```
"{书名}" 全文免费阅读
"{书名}" txt 下载
"{书名}" 最新章节
"{书名}" 笔趣阁
"{书名}" 完整版
"{书名}" 无删减
```

**有作者名时**（作者名能大幅提高命中率）：

```
"{书名}" {作者名}
"{书名}" {作者名} txt
```

**正版平台关键词**（用于找"最全"的源，哪怕收费）：

```
"{书名}" 番茄 / 七猫 / 起点
"{书名}" 晋江 / 起点 / 长佩 / 米国度
```

**技巧**：
- 书名里的特殊符号（如 `[1vN H]`、`（NP）`）搜索时保留或删掉各试一次，因为各站收录的书名格式不同。
- 搜索结果优先看「书籍详情页/目录页」而非首页，直接能判断章节数。
- 若中文搜索命中差，尝试 `site:` 限定到已知站点域名。
- **用作者名 + 简介甄别同名干扰书**：热门题材常出现大量标题高度相似的同名书，必须靠**作者名**和**简介首句**双重比对才能锁定目标，只看书名极易抓错书。

### 搜索盲区与「能搜到 ≠ 能抓取」（重要）

`web_search` 有覆盖盲区，**搜不到不代表不存在**。同时，「能否搜到」和「能否抓取」是两个**独立维度**，组合成四种情况：

| 站点类型 | 能否搜到 | 能否抓取 | 实例 |
|---------|:-------:|:-------:|------|
| SSR + 无防护 | ✅ | ✅ | 传统服务端渲染站 |
| SSR + Cloudflare | ✅ | ❌ | 被 Turnstile 拦截的站（403） |
| SPA + 无防护 | ❌ | ✅ | 纯前端渲染 + 加密 API 的站 |
| SPA + Cloudflare | ❌ | ❌ | 最难，直接放弃 |

- **SPA / hash 路由站点搜不到**：纯客户端渲染站（URL 形如 `https://example.com/#/book/12345/`）对搜索引擎不可见——爬虫不执行 JS，hash 后的路径甚至不发给服务器，具体书籍页根本不会被收录。这类站往往内容最全。
- **动态镜像域名搜不到**：镜像站会频繁更换域名（`xxx1` → `xxx2` → ...），搜索引擎来不及稳定收录。
- **能搜到 ≠ 能抓取**：SSR 站能被收录、搜到，但可能套了 Cloudflare（返回 403「Just a moment...」），照样抓不了。

**补救**：

1. 若用户提到具体域名线索，优先直接要网址，走方式一。
2. 搜索时加站点类型词（如「书屋」「阅读」），定位当前活跃的 SSR 镜像站——品牌词能搜到，但具体书籍页搜不到。
3. 意识到搜索只能覆盖 SSR 站；若搜索到的源都不全或都被 Cloudflare 挡住，主动问用户是否有已知的站或网址。

## 2. 候选站点评估

对搜索结果里的候选站（免费站、正版站、聚合站等），逐个快速探测。**只需看目录页，不必先抓正文**：

| 评估维度 | 怎么看 | 判定 |
|---------|--------|------|
| 章节完整度 | 目录页章节数、是否「完结」、最新章节更新时间 | 章节越多越新越好 |
| 乱码情况 | 抓 1-2 章正文看是否有防盗水印、编码乱码 | 乱码多的降权 |
| 是否收费 | 章节页是否要登录/付费（正版站） | 免费优先 |
| 可抓性 | SSR/CSR？Cloudflare？登录？代理？（`references/site-detection.md`） | 无 Cloudflare 优先 |

评估技巧：对每个候选站运行 `scripts/probe_site.mjs`，再抓一章正文看质量。

**章节数必须实测**：搜索结果 snippet 里的「18章节」「5万字」等信息常过时或不准确，必须以实际打开目录页得到的章节数为准。

**访问失败降级链**：`web_fetch` 对很多小说站会返回 405 / fetch failed（反爬或连接问题）。按顺序降级重试：

1. `web_fetch`（最快，但常失败）
2. Node 原生 `fetch` 带 UA + GBK 解码（即 `scripts/probe_site.mjs` 的做法）
3. Playwright（需代理或需 JS 渲染的站；Chrome 默认走系统代理）

## 3. 资源比对与选择

按优先级排序：

1. **免费 + 章节最全 + 无乱码 + 无 Cloudflare** → 最优，直接用
2. **免费 + 章节较全** → 备选，可作基础章节来源
3. **正版收费 + 章节最新最全** → 作「补最新/缺失章节」来源

## 4. 正版 + 盗版拼接

常见场景：免费站缺最新章节，正版站有更全后续但部分章节收费。

**拼接策略**：

1. 从免费盗版站抓取基础章节（大头）。
2. 从正版站抓取缺失/最新章节（需用户提供 cookie 登录，注入方式与 domain 注意事项见 `references/site-detection.md` 与 SKILL.md 的 Key Lessons）。
3. 按章节顺序拼接，抓不到的章节用占位标记 `（本章在源站无正文内容）` 占位，后续可补（见 `references/engineering.md` 增量更新）。

## 5. 给用户出方案（先汇报再动手）

搜索比对完成后，**先向用户汇报方案，征得同意再开始抓取**。汇报要点：

- 找到的最优源（站名、章节数、是否免费、有无乱码）
- 若需拼接：哪部分用哪个源、是否需要 cookie
- 预估结果（章节数、字数）

示例汇报：

> 找到两个候选源：
> ① A 站（免费，128 章，无乱码，但缺最新 3 章）
> ② B 站 正版（需你的 cookie，有最新 131 章）
> 建议：从 A 站抓 1-125 章，用你的 cookie 从 B 站补 126-131 章。
> 是否按此方案执行？

用户确认后再进入 SKILL.md 的 Workflow Decision Tree 逐源抓取。
